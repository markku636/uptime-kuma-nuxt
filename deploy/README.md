# Kubernetes deployment

The multi-node production path uses an immutable application image on every API/worker Pod and a shared external PostgreSQL16 database. Application Pods have no shared filesystem dependency. Two API replicas serve HTTP/WebSocket; two workers claim PostgreSQL leases and fence every accepted result. Worker IDs are generated per process, not configured NODE_ID partitions. API sockets receive shared committed state through PostgreSQL LISTEN/resync. Editors/owners must still select workspace/environment; platform runtime diagnostics are separate.

Build `docker build -t YOUR_REGISTRY/uptime-api:REVISION .`, publish through your authorized registry workflow, generate a private Secret from `k8s/base/secret.yaml.example`, run the revision-specific migration Job and verify Complete **before** updating Deployments. Replace the placeholder image in Kustomize with an immutable tag/digest and set the correct public URL/allowed origins. Never apply example secrets unchanged. Base Deployment/probe templates and migration examples do not migrate/seed in each replica.

`kubectl kustomize deploy/k8s/base` renders a preferred hostname spread, suitable for a single-node development cluster. `kubectl kustomize deploy/k8s/overlays/multi-node` adds per-role hostname spread with maxSkew1/minDomains2/DoNotSchedule. It requires at least two eligible worker nodes and spreads the two API Pods and two worker Pods independently. Rolling updates retain maxUnavailable0/maxSurge1; hostname balancing can place a surge alongside an existing Pod without the deadlock of mandatory one-Pod-per-host anti-affinity. No node provisioning, cluster discovery or monitor pinning is implied.

For high availability, PostgreSQL, its backups and storage must also survive node loss. The examples do not turn a single PostgreSQL PVC into an HA database. Keep network latency, connection capacity (two APIs/two workers about38 configured connections including listeners plus migration/admin margin), worker concurrency and safe shutdown budgets visible. readiness checks the database; liveness only checks the process.45-second termination grace covers cancellation/drain and bounded database cleanup. No Pod needs a service-account token, privileged capability, hostPath, host networking or runtime socket.

The operational Helm chart at `helm/uptime-api` has two modes:

- `application.mode=image`, `application.image=YOUR_IMMUTABLE_IMAGE`, `postgres.enabled=false`: shared external PG, no artifact PVC, optional strictNodeSpread for multi-node deployment.
- `application.mode=artifact`: task-owned demo only, official Node24 base and a verified SHA release on local-path RWO PVC. That storage constrains Pods to one node. It proves multi-replica application coordination, **not multi-node scheduling or node HA**.

Demo stage gates: A database/Secret; B SHA/byte-verified artifact loader; stop the temporary artifact server; C local native-Prisma SELECT1 then migration Job; D API/worker rollout from immutable local release. Both migration and app require a matching completed release marker. Final Pods do not download artifacts. Keep persistent demo DB/PVC and five paused demo monitors; remove only explicitly owned transient test fixtures. See GITOPS_DEMO_DEPLOYMENT_PLAN.md and validation reports for actual evidence.

The artifact includes .output, complete locked dependencies, Prisma migrations, runtime check/migration scripts and REST demo bootstrap. Its manifest records Node/platform/architecture, package-lock hash, tracked diff hash and a sorted working-tree digest including untracked source. The archive has an independent SHA256. The loader uses a UUID attempt directory, rejects escaping paths/links/devices, validates bytes/hash before extraction and atomically installs a release. Interrupted attempts cannot collide with a later PID1 retry.

Dockerfile image build, built-image runtime, and Kubernetes artifact runtime are reported separately. Rendering manifests is not evidence that multiple physical nodes were exercised. The currently available test cluster has one Ready node; an actual cross-node failover test needs a second eligible node and a reachable immutable image.
